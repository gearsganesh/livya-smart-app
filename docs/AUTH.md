# LIVYA Authentication

Step 2 uses Supabase Auth as the identity provider and FastAPI as the protected application API.

## Supported authentication

- Email/password
- Google OAuth
- Apple Sign In
  - Native Apple Authentication on iOS
  - Supabase OAuth/deep-link flow on Android

## Architecture

```text
Expo app
  |
  | Supabase Auth
  v
Supabase Auth -> JWT access token + refresh token
  |
  | Authorization: Bearer <access token>
  v
FastAPI AuthMiddleware
  |
  +--> JWT verification through Supabase JWKS
  |
  +--> /api/v1/auth/me
  |
  v
PostgreSQL / Supabase RLS
```

## Environment

### Mobile

Create `apps/mobile/.env` from `.env.example`:

```bash
EXPO_PUBLIC_API_BASE_URL=http://localhost:8000/api/v1
EXPO_PUBLIC_SUPABASE_URL=https://tiywldtrchjnmkkjgwmy.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

### FastAPI

Create `services/api/.env` from `.env.example`:

```bash
APP_ENV=development
DATABASE_URL=postgresql+asyncpg://livya:livya@localhost:5432/livya
CORS_ORIGINS=["http://localhost:8081","http://localhost:19006"]
SUPABASE_URL=https://tiywldtrchjnmkkjgwmy.supabase.co
SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Never commit secret/service-role keys.

## Supabase provider configuration

Enable Email in Authentication > Providers.

Enable Google and Apple in the same section and configure their provider credentials in Supabase. Add the LIVYA deep-link callback/redirect URL to the Supabase Auth URL configuration.

The mobile app uses the `livya://auth/callback` scheme generated by Expo Linking. For production, configure the exact production redirect URL(s) used by the iOS and Android builds in Supabase's redirect allow-list.

For iOS Apple Sign In, the Expo Apple Authentication capability is enabled in `app.json`. Apple Developer configuration and the Supabase Apple provider must be completed before production sign-in will work.

## API routes

- `POST /api/v1/auth/signup`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `GET /api/v1/auth/me`

The first three endpoints proxy authentication to Supabase Auth. Protected routes require a valid Supabase bearer token.

## Database security

`profiles`, journal entries, AI conversations/messages, health metrics, and processing logs have RLS enabled. User-owned data is restricted by `auth.uid()`. Staff access is mediated by the database `is_staff()` security-definer helper.

`processing_logs` are intentionally metadata-only. Do not store prompts, report contents, PHI, access tokens, credentials, or raw AI payloads in this table.
